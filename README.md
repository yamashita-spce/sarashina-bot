# Sarashina Discord Bot

国産LLM **Sarashina** (SB Intuitions) の API を使い、Discord の指定チャンネルに投稿された質問へ自動で回答する Bot です。

## 機能

- 指定チャンネル（とその中のスレッド）への投稿に、Sarashina（`sarashina3-mini`）が返信で回答
- **チャンネルの文脈を踏まえて回答**：質問のたびにチャンネルの直近の会話を `sarashina3-nano` に要約させ、その要約＋直近の発言数件を背景コンテキストとしてプロンプトに加えてから回答する（「それっていつだっけ？」のような質問にも答えられる）
- **処理中ステータスのアニメーション表示**：スピナー・切り替わる見出し・進捗バーで「文脈を読んでいる」「回答の順番待ち（あと約N秒）」「回答を書いています」などを表示
- **回答は一気に表示**：回答が完成したら新しいメッセージとして一度に投稿し、ステータスのメッセージは削除する（ステータスに上書きしない）。チャンネルには回答だけが残る
- **mini のレートリミット対策**：mini（6 RPM）の送信枠を予約制で管理し、混雑時は何秒後に回答できるかを表示する
- **速さより質を優先**：回答前に nano が多段階で考え（思考メモを mini に渡す）、mini の回答案を nano がチェックして、重大な問題（事実・計算の誤り、質問に答えていない等）があれば mini が1回だけ書き直す
- **パーソナライズされた処理中表示**：質問ごとに nano が作業計画を立て、「方程式を立てて考えています」「計算結果を確認しています」のように**その質問に合わせた作業ラベル**、4段階の進み具合（集める→考える→確かめる→書く）、誰のどの質問への回答か、見つかった過去の会話などを表示
- **チャンネル横断検索**：「〇〇の話どこだっけ？」「〇〇さんと議論してた内容をまとめて」「#お知らせの内容をまとめて」のような投稿を自動で検索として扱い、サーバー内の過去ログから該当する発言を探して**発言へのリンク付き**で返す（下記「チャンネル横断検索」参照）
- **RAG（過去の会話を踏まえた回答）**：普通の質問でも、サーバー全体の過去の会話から質問に役立つものを探して mini に渡し、使った箇所には `[参1]` のような発言へのリンクを付ける（関係なければ使わない）
- Bot の回答に「返信」すると、返信チェーンを会話履歴として引き継いで続きの会話ができる
- 2000文字を超える回答は分割して投稿

## セットアップ

### 1. Sarashina API キー

https://chat.sarashina.ai/dashboard/api-keys で発行し、`.env` の `SARASHINA_API_KEY` に設定します。

### 2. Discord Bot の作成

1. [Discord Developer Portal](https://discord.com/developers/applications) で New Application を作成
2. **Bot** タブで Token を発行 → `.env` の `DISCORD_BOT_TOKEN` に設定
3. 同じ Bot タブで **MESSAGE CONTENT INTENT** を ON にする（必須）
4. **OAuth2 > URL Generator** で scope `bot` を選び、権限に
   `View Channels` / `Send Messages` / `Send Messages in Threads` / `Read Message History` を付けて URL を生成し、サーバーに招待（検索で過去ログを読むため、検索したいチャンネルの閲覧・履歴閲覧権限が必要）
5. Discord の「開発者モード」を ON にし、対象チャンネルを右クリック →「チャンネルIDをコピー」→ `.env` の `DISCORD_CHANNEL_IDS` に設定（複数はカンマ区切り）

### 3. インストールと起動

```bash
cp .env.example .env   # 値を設定
uv venv .venv
uv pip install -p .venv -r requirements.txt
./run.sh
```

## 常時起動 (systemd)

ユーザー単位の systemd サービスとして登録済みです（PC起動時に自動起動、落ちても10秒後に自動再起動）。
`loginctl enable-linger` 設定済みのため、ログアウト中も動き続けます。

```bash
systemctl --user status sarashina-bot     # 状態確認
tail -f logs/bot.log                      # ログをリアルタイム表示 (Ctrl+C で抜ける)
systemctl --user restart sarashina-bot    # 再起動 (.env やコードを変更したとき)
```

### ログ

ログは `logs/bot.log` に出力され、毎日0時にローテーション、`LOG_RETENTION_DAYS`（既定7日）より古いものは自動削除されます。systemd の journal には起動・停止の記録とクラッシュ時のエラーしか残りません。

```bash
tail -f logs/bot.log    # ログをリアルタイム表示
```

### 停止する方法

```bash
systemctl --user stop sarashina-bot       # 一時停止 (PC再起動すると、また自動起動する)
systemctl --user disable --now sarashina-bot  # 停止＋自動起動もやめる
systemctl --user enable --now sarashina-bot   # 再び常時起動に戻す
```

### 新しい環境でサービスを登録する場合

```bash
mkdir -p ~/.config/systemd/user
ln -sf "$PWD/sarashina-bot.service" ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now sarashina-bot
loginctl enable-linger "$USER"   # ログアウト中も動かす
```

※ `sarashina-bot.service` 内のパスは `/home/shita/private/salashina` 固定です。別の場所に置く場合は書き換えてください。

### チャンネル文脈と回答の方針

- **直近のやり取りを最優先**：質問の直前 `CONTEXT_RECENT_MESSAGES` 件の発言を、要約せずそのまま会話履歴（他の人の発言は「名前: 本文」、Bot の回答は assistant）として mini に渡す。「それ」「こういうところ」や、前の回答への指摘・追加の依頼を正しく解釈するため
- **それより前の会話は要約で補う**：前回以降の新着発言を `sarashina3-nano` で差分要約し（チャンネル/スレッドごとにメモリ保持）、「関係する場合だけ参考にする」背景としてシステムプロンプトに付ける
- **回答の方針（既定のシステムプロンプト）**：答えを最初に簡潔に書く／前置き・お礼・謝罪・共感の決まり文句を書かない／普通の「です・ます」調で大げさな表現を使わない／関係のない過去の話題を持ち出さない／批判には言い訳せず内容で応える
- 小さいモデルはプロンプト末尾の指示ほど守るため、最後のユーザー発言の直後に短い確認（前置き禁止・指示語の対象を先に特定）を付けている
- それでも付きがちな「ご質問の意図を理解しました。〜についてですね。」等の書き出しは、生成後にコードで取り除く

### Discord 上での表示

質問すると Bot はまずステータスのメッセージで返信し、約1.2秒ごとに表示が切り替わります。思考の中身は表示しません。

```
⠙ 💭 方程式を立てて考えています..
-# ✅ 集める → ⠙ 考える → ▫️ 確かめる → ▫️ 書く
-# ▰▰▱▱▱▱▱▱▱▱▱▱▱▱ 1秒 · すずきさんの「Bさんの年齢」
-# 📎 #チャット の過去の会話を2件見つけました
```

- 1行目のラベルは、質問ごとに nano が立てた作業計画（`PLAN_LABELS_PROMPT`）から。4段階それぞれに「その質問に合わせた具体的な作業」のラベルを作らせている（計画が間に合わない間は汎用ラベル）
- 2行目は4段階の進み具合、3行目は進捗バー・経過秒数・残り時間（順番待ちのとき）・誰のどの質問か、4行目以降は見つかった過去の会話や混雑・書き直しなどの状況メモ
- 検索のときは「今どういう検索をしているか」を**一言コメント**で表示し、目まぐるしく変わらないよう**10秒に1回まで**切り替える（例: 「「ラーメン」の話を探しています」→「「青葉 ラーメン 東京」という切り口でも探しています」→「見つかった会話を読み比べて、関係あるものを選んでいます」）
- **待ち時間も「考えている」表示**：mini のレート制限で待つ間は、「見つかった会話を読み比べています」「「転職」の要点を整理しています」など質問に合わせた思考ラベルを10秒ごとに切り替えて表示し、残り時間は進捗バーの横に小さく出す
- 回答が完成したら新しいメッセージで一気に投稿し、ステータスのメッセージは削除（ステータスに上書きしない）
- 再起動などで処理が中断されステータスが残った場合は、Bot 起動時に対象チャンネルの直近100件を確認して自動で片付ける

### 回答のチェックと書き直し（`ANSWER_CHECK_ENABLED`）

- mini の回答案を nano がチェックする。「回答案を見ずにまず自分で解く → 回答案と比べる」手順にしている（単に「誤りはあるか」と聞くと、nano も mini も明らかな誤りを見逃したため）
- 検証: 「月曜の100日後は金曜日」「日本一高い山は北岳」は書き直し判定、正しい回答には指摘なし
- 重大な問題があったときだけ、指摘を添えて mini が1回だけ書き直す（mini の枠をもう1回使う）

### mini のレートリミット対策

- 送信枠を予約制で管理する（`RateLimiter.reserve`）。質問ごとに「自分の番が何秒後か」が分かるので、ステータスに残り秒数を表示し、予約時刻ちょうどに送信する
- 予約時刻に送るため、通常は 429 エラーにならない（万一 429 になった場合は1分待ってリトライ）

### 思考フェーズ（`THINKING_ENABLED`）

- Sarashina API には長考（reasoning）モデルが無い。mini（AIME 2025: 0.60）は nano（0.38）より賢いが 6 RPM しかないため、思考は 60 RPM の nano に任せ、mini は最終回答の1回だけに使う
- nano が「思考（意図→文脈→分解して検討→検算→方針）→ 見直し →（mini の順番待ちに余裕があれば）回答設計」と多段階で考え、その思考メモを mini のシステムプロンプトに渡す。mini には「下書きなので自分で検証し、誤りは正す」よう指示
- mini の順番待ちの時間を nano の追加思考に充てる。ステータスは 💭 思考 → 🔁 見直し → 🧭 回答設計 → ⏳ 待機 と切り替わる。最短 `THINKING_MIN_SECONDS` 秒は考える

効果検証（2026-10-14）:
- 正解が明確な10問（計算・論理・文字数え等）で「mini 単体」と「nano 思考＋mini」を比較 → mini 単体 9/10、思考あり 10/10（差は strawberry の r の数え上げ1問のみ）
- 効果は小さく有意とは言えない一方、遅延と nano 呼び出しが増えるため、一旦は既定 off にしていた
- その後「回答が遅くなってもよいので、しっかりした回答を優先する」方針になり、既定 on に戻した（回答チェックと組み合わせ）

## チャンネル横断検索

### 使い方

対象チャンネルにふつうに書き込むだけで、検索か普通の質問かを自動で判定します。`検索:` や `🔍` で始めると必ず検索になります。

- 「どこ」「まとめ」「話した」「発言」「いつ」などの手がかりを含まない投稿は、検索の判定をせずに普通の質問として扱う（Bot の回答への感想・指摘が検索扱いになるのを防ぐ）
- 直前が検索結果なら、「古すぎる」「もっと最近の」「他には？」のような追加の依頼は、直前の検索条件（人・話題・チャンネル）を引き継いで検索し直す
- 「山下の発言」のような人名は、索引にある発言者名の一覧から nano が対応付ける（例: 山下 → yama_spec）

| 投稿の例 | 出力 |
|---|---|
| 「ラーメンの話どこでしてたっけ？」 | どのチャンネルで・いつ・誰が・どんな流れで話していたかを**文章で答え**、末尾に参考にした発言（リンク付き）を添える |
| 「転職について話してた内容をまとめて」 | 話題ごとの要点を**文章で答え**、末尾に参考にした発言を添える |
| 「お知らせで告知してた内容をまとめて」 | チャンネル名で絞り込んでまとめる |
| 「ボルダリングの話どこだっけ？」（該当する会話が無い） | 何往復探しても根拠が無ければ、**何を補足してほしいか聞き直す**（「〜という発言がありましたが、この会話でしょうか？いつ頃・どのチャンネルか分かれば教えてください」など） |
| 「お疲れ！今日も暑いね」 | 検索せず、普通の会話として返す |

出力の形:
```
（依頼への答えを文章で。根拠には [1] [2] のような短い番号）

-# 参考にした発言
-# [1] #チャット 2024/11/27 12:08 やんゆー「本場の博多ラーメン食べれることだけが…」[→ 移動](リンク)
-# [2] ...
```

- 本文には短い番号だけを付け、リンクは末尾の「参考にした発言」にまとめる（本文を読みやすくし、2000文字の上限も節約）
- **回答の精査（見つかったらすぐ答えるのではなく、質問に一番答えている案を選ぶ）**：
  1. mini に回答案を3通り書かせる（Chat API の `n` パラメータ。1リクエストで複数生成するので、レート制限の消費は1回分）
  2. rerank（`GENERAL_QA`）で各案の「**回答度** = 質問への答えになっている度合い」を測る（下記）
  3. nano（審査員）が、根拠の会話と回答案を読み比べ、根拠と食い違う案を指摘し、依頼が求めていることに最も直接答えている案を推す
  4. 根拠と食い違う案を除いた中で回答度が最も高い案を採用（審査員の推しが回答度で僅差なら審査員を優先）
  5. 審査で「依頼に答えるのに大事な観点が欠けている」と判定されたら、その観点で追加検索し、新しい会話が見つかれば集め直して書き直す（1回まで）

#### 回答度（rerank で「質問への答えになっているか」を測る）

rerank のスコアは同じ話題なら 0.9999… に張り付くため、そのままでは差が見えない（当初「全案 1.0 で使えない」と判断していた）。logit（log(p/(1-p))）に直すと、**質問への答えになっているか**で綺麗に分かれる。一方で、事実の正誤（根拠と合っているか）は測れない（誤った回答も 1.0 になる）ので、そこは nano の審査で見る。

| 質問 | 答えている | 一部だけ答えている | 同じ話題だが答えていない |
|---|---|---|---|
| 名古屋に行く話ってどうなったっけ | 15.3（結末まで） | 13.5（計画だけ）/ 13.6（前置きが長い） | 2.4（観光案内） |
| ラーメンの話どこでしてたっけ | 20.7（場所を答える） | 10.1（内容だけ） | 5.2（一般論） |

普通の質問の回答チェックでも、回答度が `ANSWER_MIN_SCORE`（既定 7）未満なら「質問に直接答えていない」として mini が書き直す（例: 「Pythonでリストを逆順にする方法は？」に Python の一般的な説明だけ → 6.1 で書き直し）。

- **極力一発で答える。聞き直しは最終手段**：
  1. 通常の検索（2〜6往復）で根拠のある会話が見つかれば、そのまま答える。直接の言及が無くても関係する話があれば「直接の言及はありませんが、〜」の形で答える
  2. 根拠が足りなければ（話題の語がどの本文にも出てこない／mini が引用なしで「見当たらない」と答えた）、**十分かどうかに関わらず5往復・条件も広げ切って粘り強く探し直し**、関係する会話があればそれで答える
  3. それでも関係する会話が1件も無いときだけ、何を補足してほしいか聞き直す
- 普通の質問で過去の会話を参考にした場合も、同じ形で末尾に「参考にした過去の会話」を添える

検索結果は、**質問した人が閲覧できるチャンネルだけ**から返します（見えないチャンネルの内容は漏らしません）。

### 仕組み（何往復もして、十分な情報が集まってから答える）

```
投稿 ─▶ nano: 検索か判定し、話題・キーワード・人・チャンネル・期間を JSON で抽出
          │（検索でなければ通常の回答へ）
          ▼
  ┌─ n回目の検索: embedding（意味の近い会話）＋キーワード一致で候補を集める
  │      ▼
  │   rerank: 元の依頼との関連度で並べ替え、上位24件を候補として保持
  │      ▼
  │   nano: 「見つかった会話で依頼に十分答えられるか」を判定し、足りなければ
  │         不足している情報と次の検索語（言い換え・関連語・見つかった会話の手がかり）を最大2つ提案
  │      ▼
  │   言い換えでも新しい会話が見つからなくなったら、条件を広げる（期間 → チャンネル → 人）
  └─ 十分になるまで繰り返す（最低 SEARCH_MIN_ROUNDS 回、最大 SEARCH_MAX_ROUNDS 回）
          ▼
       nano: 上位10件を読んで「本当に関係あるか」を判定し、会話の中心となる発言（リンク先）を選ぶ
          ▼
       根拠あり → （まとめる場合は前後の会話も読み足し）mini が依頼への答えを文章で書き、末尾に参考にした発言
       根拠なし → mini が何を補足してほしいか聞き直す
```

- **十分な情報が集まってから答える**：根拠が足りなければ検索語を変えて何往復もする。それでも根拠が無ければ「見つかりませんでした」ではなく、何を補足してほしいか聞き直す
- **待ち時間も検索に使う**：まとめる場合は mini の回答枠を最初に予約し、空くまでの間は十分でも検索を続けて情報を厚くする
- 例（実データ）：「転職について話してた内容をまとめて」→ 1回目「転職」→ 2回目「転職活動 進捗」「未経験 法人営業 転職」→ 3〜4回目「公的就職支援」…と、見つかった会話の手がかりで広げてからまとめる
- rerank のスコアは無関係な会話でも 0.9 以上になることがあり、しきい値に使えないため、最後に nano に関連判定させている
- 実データは URL・画像・相づちが多いので、リンク先は nano に会話全体を読ませて中心の発言を選ばせている
- Bot と会話するチャンネル自体は取り込まない（Bot への依頼文が検索結果や次の検索語に混ざるため。`SEARCH_INDEX_BOT_CHANNELS=true` で取り込む）

### 普通の質問での RAG

Sarashina API には、ファイルや会話を預けると検索してくれる仕組み（OpenAI の File Search / Vector Store のようなもの）は無い。そのため、提供されている部品を組み合わせて RAG を構成している。

```
質問 ─▶ embedding で過去の会話（チャンク）から候補15件 ─▶ rerank で上位6件
     ─▶ nano が「質問に答えるのに本当に役立つ具体的な情報があるか」を判定（URL だけの発言は根拠にしない）
     ─▶ 役立つ会話（最大3件）を [参N] 付きで mini のシステムプロンプトへ ─▶ mini が回答
     ─▶ 回答中の [参N] を発言へのリンクに変換し、末尾に参照した会話を添える
```

- 質問しているチャンネルの直近1時間の会話は、会話履歴として別に渡しているので RAG の対象から除く
- 挨拶や一般常識の質問、関係する会話が無い場合は何も足さない
- mini はネットや最新情報にアクセスできないため、天気・ニュースなどは推測で答えず「分からない」と答えるようにしている
- 1質問あたり embedding 1回 + rerank 1回 + nano 1回が増える（mini の回数は変わらない）

### 取り込み（インデックス）

**保存とベクトル化を分けている**。埋め込み API は1リクエスト1テキスト・60 RPM なので、ベクトル化を待っていると全チャンネルが揃うまで何時間もかかるため。

1. **保存（API を使わないので速い）**：発言を会話のまとまり（最大12件・1200文字、15分以上空いたら区切る）に分けて SQLite に保存。保存した時点でキーワード検索の対象になる
   - **リアルタイム**：新しい発言はイベントで受け取り、会話が3分途切れたら（または12件たまったら）保存
   - **定期巡回**（`SEARCH_INDEX_INTERVAL` 秒ごと）：最近発言のあったチャンネルから順に、取りこぼし（Bot 停止中の発言など）を補い、その後で過去ログを500件ずつ遡る。遡るのは `SEARCH_BACKFILL_DAYS` 日（既定1年）まで、1チャンネル最大 `SEARCH_BACKFILL_LIMIT` 件
2. **ベクトル化（裏で順次）**：未処理の会話を**新しい順に** `sarashina3-embedding` でベクトル化（先頭256次元に切り詰めて保存）。検索用に20枠を残して空き枠だけ使う（約40件/分）
- 初回は全36チャンネル・約7,000件の保存が約2分で終わり、ベクトル化は新しい会話から1時間ほどかけて進む
- 発言の削除・編集も反映。Bot の発言は取り込まない。索引は `data/search.db`（再起動しても続きから）

### 検索結果の偏り対策
- 期間の指定が無い検索は直近 `SEARCH_DEFAULT_DAYS` 日（既定1年）を探し、見つからなければ全期間で探し直す
- 1回の結果に同じ人の発言は `SEARCH_MAX_PER_AUTHOR` 件（既定2件）まで（人を指定した検索は除く）。発言の多い人ばかりが並ばないようにするため
- 英字のキーワードは単語単位で照合（「ai」が「mail」「said」に一致しない）
- nano が無関係と判定した会話は、検索語句そのものを含む場合を除いて出さない

### API 呼び出し回数

- 普通の質問: 振り分け(nano, 手がかり語がある時) + 作業計画(nano) + 要約(nano, 新着がある時) + RAG(embedding・rerank・nano 各1回) + 思考(nano, 最大3回) + 回答(mini) + チェック(nano) + 書き直し(mini, 問題があった時だけ)。mini は1〜2回
- 検索: 振り分け(nano) + 1往復あたり embedding 1〜2回・rerank 1〜2回・判定(nano) 1回（2〜6往復）+ 関連判定(nano) + 回答案3通り(mini, 1回) + 審査(nano) +（欠けがあれば）追加検索と書き直し(mini, 1回)

## 構成

```
bot/main.py       Discord Bot 本体（メッセージ受信・履歴構築・思考・回答投稿・残骸の片付け）
bot/sarashina.py  Sarashina API クライアントとモデル別レートリミッター
bot/context.py    チャンネル会話の要約（背景コンテキスト）管理
bot/search.py     チャンネル横断検索（振り分け・候補収集・rerank・関連判定・リンク付き出力・まとめ）
bot/search_index.py  検索インデックス（SQLite＋ベクトル）とバックグラウンド索引付け（Indexer）
data/             検索インデックス（search.db）
bot/thinking.py   思考プロンプト、処理中ステータスの描画（ThinkingView）、アニメーション（Animator）、編集間隔制御（ThrottledEditor）
logs/             ログ（日次ローテーション、自動削除）
run.sh            手動起動スクリプト（systemd 稼働中は二重起動しないこと）
sarashina-bot.service  systemd ユーザーサービス定義
```
